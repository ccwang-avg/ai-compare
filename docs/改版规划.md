# AI 竞品分析报告改进规划

## 1. 项目定位

本项目不再定义为“AI PM 竞品分析工作台”，而改为一份更清晰、更适合作品集展示的：

```text
AI 竞品分析报告
```

定位原则：

- 这是一个竞品分析网页，不是 AI 工具导航站。
- 这是一个研究型展示页，不是带后台感的工作台。
- 产品经理视角保留在分析方法中，不放在站点标题中强调。
- 页面目标是展示结构化分析能力，而不是做主观排名。

适用场景：

- 面试作品集展示
- 个人研究项目展示
- AI 产品横向分析汇总

## 2. 本次改版的核心目标

本次改版聚焦四件事：

1. 把页面主题统一为“AI 竞品分析报告”
2. 把“评分主导”改成“结构化判断主导”
3. 把竞品分类改为“主类型 + 能力标签”
4. 把前端风格改成更强的“研究报告感”

改版后的页面应重点体现：

- 能说明为什么选这些竞品
- 能说明这些竞品的差异在哪里
- 能说明判断依据来自哪里
- 能用图表和表格提升可读性
- 能在面试中经得起追问

### 2.1 前端执行必须遵循的 skill

本项目后续前端改版明确遵循以下两个 skill：

- `frontend-design`
- `browser:control-in-app-browser`

分工如下：

- `frontend-design`：用于约束页面的设计方向、审美质量、排版层次和实现风格
- `browser:control-in-app-browser`：用于本地页面验证、交互检查、视觉复查和验收

执行要求：

- 前端实现时，优先遵循 `frontend-design` 的设计原则
- 前端完成后，必须使用 `browser:control-in-app-browser` 检查真实页面效果

## 3. 评分的意义与最终处理方案

### 3.1 评分的意义

评分不是为了给产品“打榜”，而是为了服务横向比较。

它的意义只有三个：

1. 压缩复杂信息
2. 提供统一刻度
3. 帮助读者快速扫读差异

但评分不能成为页面主逻辑，因为竞品分析的重点不是“谁分更高”，而是：

- 产品主战场是什么
- 目标用户是谁
- 核心场景是什么
- 差异化优势是什么
- 能力边界在哪里
- 商业化路径是否清晰

### 3.2 最终方案

本项目最终采用：

```text
弱化数字评分，强化结构化判断
```

具体策略：

- 页面主体不以总分、排名、榜单为核心
- 保留横向比较能力，但不做“第一名”叙事
- 优先用主类型、能力标签、场景、优势、风险来表达差异
- 如需可视化比较，优先使用等级判断或热力矩阵，而非总分榜

### 3.3 是否保留评分

最终建议：

- 首页和主叙事中不突出数字评分
- 对比区可以保留“研究性判断”
- 形式优先采用：

```text
强 / 较强 / 中等 / 较弱
```

而不是精确到 `1-5` 的硬分值。

如果后续为了图表表达需要保留数值，也必须明确标注：

```text
以下判断基于公开资料、官方页面与通用产品体验整理，仅用于横向比较，不代表权威测评结果。
```

## 4. 联网调研方案

本次改版允许联网调研，且应将联网调研作为内容可信度的重要来源。

调研原则：

- 优先使用官方站点、官方产品页、官方定价页
- 补充少量高可信二级资料用于交叉验证
- 对关键事实保留来源链接
- 对存在时效性的内容标注更新时间

建议优先调研的信息：

- 产品官网
- 定价结构
- 官方功能说明
- 企业版能力
- 编程或 Agent 能力说明
- 多模态能力说明
- 最新产品定位变化

建议首批调研竞品范围：

- ChatGPT
- Gemini
- Claude
- Perplexity
- Cursor
- GitHub Copilot
- Kimi
- 豆包

如需突出编程 Agent，可在后续版本将 `Claude Code` 作为独立样本补入。

### 4.1 样本纳入标准

首批竞品不是随意挑选，纳入应满足以下条件：

- 在对应赛道中具有代表性
- 具备较高用户认知度或行业讨论度
- 能覆盖通用助手、AI 搜索、编程 Agent、中文助手、生态型助手等主要类型
- 近一年仍在持续更新或具备持续活跃的产品形态
- 能获取到足够的公开资料、官方页面或定价说明

排除标准：

- 信息过少，无法形成有效判断
- 与已纳入样本高度重叠，分析增量很低
- 产品形态不稳定，难以界定其定位
- 主要能力无法通过官方资料或公开体验验证

### 4.2 证据等级

为了控制调研可信度，后续内容判断应按证据等级使用来源：

一级证据：

- 官方网站
- 官方定价页
- 官方产品说明页
- 官方文档
- 官方博客、官方发布说明

二级证据：

- 主流科技媒体报道
- 权威行业报告
- 官方负责人公开访谈中的明确信息

三级证据：

- 社区体验帖
- 第三方测评文章
- 用户讨论区反馈

使用原则：

- 关键事实优先使用一级证据
- 二级证据用于补充上下文和交叉验证
- 三级证据只能作为体验补充，不作为核心结论唯一依据

## 5. 竞品分类体系

现有分类不够稳定，存在把“多模态”误用为产品类别的问题。

改版后采用双层结构：

### 5.1 主类型

每个产品只归一个主类型：

1. 通用助手
2. AI 搜索
3. 编程 Agent
4. 中文助手
5. 生态型助手

### 5.2 能力标签

每个产品可同时拥有多个能力标签：

- 多模态
- 长上下文
- 研究检索
- 编程协作
- Agent 执行
- 企业落地
- 中文体验
- 移动端场景
- 内容创作
- 文档处理

分类原则：

- “多模态”是能力标签，不是主类型
- “编程 Agent”可以作为主类型
- 一个产品只能有一个主类型，但可以有多个能力标签

## 7. 网页内容结构

本次执行优先做成：

```text
单页、不分页、不折叠的 AI 竞品分析报告
```

页面从上到下连续展开，减少切页和收起操作，让内容更像完整报告。

建议页面结构如下。

### 7.1 报告头部

内容包括：

- 网站标题：AI 竞品分析报告
- 副标题：从产品定位、核心场景、能力边界与商业化路径，对主流 AI 产品进行横向分析
- 样本数量
- 主类型数量
- 更新时间

### 7.2 关键发现

用 3-5 条结论概括本轮调研最重要的判断，例如：

- 通用助手的竞争焦点正在从模型能力转向工作流入口
- AI 搜索的核心价值在于降低信息获取和核查成本
- 编程 Agent 的关键差异在于是否能进入真实工程闭环

这一部分必须来自调研与结构化判断，不能写空泛口号。

### 7.3 样本概览

展示首批样本卡片，卡片信息建议只保留高价值内容：

- 产品名
- 公司
- 主类型
- 能力标签
- 一句话定位

### 7.4 分类体系说明

简要解释：

- 什么是主类型
- 什么是能力标签
- 为什么不把“多模态”当成产品类别

这一部分用于增强页面的分析逻辑自洽性。

### 7.5 图表区

建议第一版使用 3 类图表：

1. 主类型分布图
2. 能力标签热力矩阵
3. 代表产品能力对比图

图表原则：

- 以可读性优先，不追求花哨
- 热力矩阵优先于复杂交互图
- 图表服务于判断，不单独堆视觉

图表执行清单：

- 图表 1：主类型分布图
- 图表 2：能力标签热力矩阵
- 图表 3：代表产品能力对比图

第一版图表要求：

- 至少完成 2 张图表
- 图表必须能支撑页面中的关键发现
- 图表颜色体系必须与整站视觉统一

### 7.6 核心对比表

这是页面最重要的结构化区域之一。

建议字段：

- 产品
- 主类型
- 一句话定位
- 代表场景
- 多模态
- 研究检索
- 编程协作
- Agent 执行
- 企业落地
- 定价结构
- 核心优势
- 主要风险

表达方式建议：

- “多模态 / 研究检索 / 编程协作 / Agent 执行 / 企业落地”使用等级判断
- 优势与风险用简短文本
- 不做总分列

表格执行清单：

- 表格 1：核心竞品对比表
- 表格 2：来源与更新时间表，可作为附加区块或补充信息

### 7.7 分产品分析

每个产品使用单独区块展开，像一页页串联的小型报告。

每个产品建议展示：

- 产品名与公司
- 主类型与标签
- 产品摘要
- 目标用户
- 核心场景
- 主要优势
- 主要短板
- 商业化与企业能力
- 分析结论
- 来源链接

### 7.8 方法说明

最后单独放一个方法说明区，明确：

- 本报告不是客观榜单
- 判断主要来自官方资料与公开体验
- 等级判断仅用于横向比较
- 内容有时间性，后续可继续更新

### 7.9 内容更新机制

既然页面支持联网调研，内容更新必须有清晰规则：

- 页面顶部展示本轮报告更新时间
- 每个产品条目保留 `updatedAt`
- 每个产品条目必须保留 `sources`
- 若官方定价、定位或关键能力变化，应优先更新对比表和关键发现区
- 新增竞品时必须补齐主类型、能力标签、来源与更新时间

## 8. 前端设计方案

本次前端不继续沿用普通 dashboard 风格，而改为：

```text
研究报告感 + 编辑部感 + 数据面板感
```

设计目标：

- 一眼看上去像认真做过研究的作品
- 信息密度高，但阅读层级清晰
- 更像报告页，不像后台系统

设计原则：

- 标题排版要更强
- 控制主色数量，避免模板化蓝白后台感
- 通过注释、小标题、标签和分隔增强专业感
- 表格和图表作为主角，卡片作为辅助
- 保持桌面和移动端都能稳定阅读

建议表现特征：

- 浅色背景但不纯白
- 深色正文
- 少量强调色
- 细边框与报告式模块分隔
- 更明显的节奏型排版

### 8.1 前端实现需要遵循的 skill 与约束

本项目的前端改版应同时参考以下两类能力：

```text
frontend-design
browser:control-in-app-browser
```

其中：

- `frontend-design` 用于约束页面的视觉方向、设计质量和实现风格
- `browser:control-in-app-browser` 用于本地页面验证、交互检查和验收

`frontend-design` 需要落实的要求：

- 先确定明确的视觉方向，再开始编码实现
- 页面必须避免通用 AI 模板感和普通 dashboard 审美
- 强调有辨识度的字体、配色、节奏、层次和背景氛围
- 页面风格应具有完整的审美立场，而不是堆叠常见组件
- 代码必须是可运行、可交付的真实前端实现，而不是静态展示稿

在这个基础上，前端开发还必须遵循当前环境中的实现约束：

- 保持设计有明确视觉方向，避免默认模板化 dashboard 风格
- 优先突出报告感、信息密度和结构层次
- 在现有项目中统一视觉变量、组件节奏和排版尺度
- 桌面端和移动端都必须可读，不允许只做桌面稿式页面
- 图表、表格、标题、注释必须形成统一风格，而不是各自独立

### 8.2 Browser skill 的使用要求

当前用于页面验证和验收的 skill 是：

```text
browser:control-in-app-browser
```

该 skill 的用途不是生成设计，而是：

- 打开本地页面
- 检查实际布局与交互
- 验证图表、表格、滚动阅读体验
- 在修改后复查桌面端与移动端效果

执行原则：

- 前端重大改动完成后，必须使用 Browser 打开本地页面验证
- 验证重点包括首页首屏、图表区、主对比表、长页面滚动节奏、移动端阅读体验
- Browser 主要用于验收和行为检查，不替代代码实现本身
- 若页面样式或布局与规划目标不符，应以 Browser 可见结果为最终修正依据之一

建议纳入前端验收流程的 Browser 检查项：

- 页面是否明显脱离默认后台风格
- 首屏是否能一眼看出“AI 竞品分析报告”的定位
- 图表是否清晰可读
- 对比表在桌面端是否完整，在移动端是否仍可用
- 长页面滚动时信息节奏是否稳定
- 是否存在样式破损、错位、拥挤或层级混乱

## 10. 面试答辩口径

这部分建议作为项目说明的统一表达口径：

- 这个项目不是客观测评网站，而是一份结构化竞品分析报告
- 页面重点不是给产品排名，而是建立一套可解释的比较框架
- 等级判断仅用于帮助读者快速横向理解差异，不代表绝对结论
- 页面设计选择服务于报告可读性和信息表达，而不是后台操作效率
- 联网调研与来源链接的引入，是为了让页面从“主观印象展示”升级为“有证据支撑的研究展示”

## 11. 非目标范围

第一阶段不做以下内容：

- 登录系统
- 在线编辑后台
- 数据库接入
- 自动爬虫
- 用户权限系统
- 实时 AI 调用生成报告

第一阶段目标是先把：

```text
可展示、可解释、可扩展的竞品分析报告页
```

做扎实。

## 13. 验收标准

第一阶段完成后，至少应满足以下验收条件：

- 页面主标题、导航和核心文案已全部替换为“AI 竞品分析报告”口径

- 主页面已实现单页、不分页、不折叠的连续阅读结构

- 页面在桌面端与移动端都可正常浏览
- 页面视觉已明显脱离默认 dashboard 风格
- Browser 验证已覆盖首屏、图表、主表格和长页面滚动体验

本次改版的最终方向已经明确：

- 主题改为“AI 竞品分析报告”
- 弱化评分，强化结构化判断
- 分类改为“主类型 + 能力标签”
- 支持联网调研并保留来源
